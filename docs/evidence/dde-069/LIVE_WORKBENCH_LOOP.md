## What this tranche closes

The canonical `FRONTEND_STUDIO_REV3.md` section 5.3 host strategy is now implemented: the six legacy Frontend Studio `WebviewViewProvider` sidebar surfaces remain compatibility shims, while the canonical React/Vite Frontend Studio opens as a central VS Code `WebviewPanel`.

The production transport is:

```text
React feature component
→ DdeHostBridge / VsCodeHostBridge
→ FrontendStudioWorkbenchPanel
→ StudioGatewayService
→ GatewayApiClient
→ mission-scoped Core /v1 read or /v1/commands
→ DDE-069 bounded domain service
```

The workbench no longer depends on `TestHostBridge` for its production host implementation. The test bridge remains a fail-closed browser harness: every dynamic read and command must be explicitly registered.

## Code-backed preview loop

The React workbench now consumes real candidate-board and screen-tree projections. A selected candidate may load a materialized preview document from Core into an iframe sandboxed with `allow-scripts` only. The iframe runtime may report `ready`, `selection`, or `runtime_error` only for its own `previewSessionId` + `contentHash`.

A persisted `LIVE` row is not sufficient for a newly opened panel to display LIVE. This browser must load the candidate document and send the content-hash handshake; Core then rechecks candidate workspace, candidate state, effective PXG revision and candidate source hash before returning LIVE.

Selection is `pxg_key`-based. The selection outline is derived from geometry attached to that stable key, and Inspector reads resolve the same key through Core. DOM index/position is not an identity path.

## Governed Inspector mutation and invalidation

Inspector property choices come from `InspectorDescriptor.legal_values`. Applying one sends `frontend.mutation.apply` with `origin=INSPECTOR`; the React UI does not write source or accepted PXG directly.

A successful mutation now additionally:

1. transitions the candidate to the governed post-mutation state;
2. clears `verification_run_id` when the candidate becomes `DIRTY` because the old verdict described pre-edit code;
3. transitions every BUILDING/LOADING/LIVE preview session for that candidate to `STALE`;
4. returns the invalidated preview-session ids;
5. causes the workbench to start a new code-backed preview, load the new document, and require a new browser LIVE handshake.

The existing accepted design is still untouched until promotion.

## VS Code host and packaging proof

`FrontendStudioWorkbenchPanel` owns the VS Code host boundary. It handles the bridge `read`, `command`, `capabilities`, `revealFile`, and notification operations. Source reveal refuses absolute paths and `..` traversal and resolves only inside the open VS Code workspace.

The extension manifest now exposes:

- `DDE Code: Open Frontend Studio Workbench`;
- `DDE Code: Set Frontend Studio Mission`;
- `dde.studio.frontendMissionId` as the explicit mission selector when a unique tracked mission cannot be inferred.

`vscode:prepublish` and `npm run package` build the React bundle before compiling the extension. The real VSIX package was produced successfully and contains:

- `extension/out/src/webviews/frontendStudioWorkbenchPanel.js`;
- `extension/ui/dist/assets/dde-studio.js`;
- `extension/ui/dist/assets/dde-studio.css`.

Stable asset names are generated by Vite; source maps are not emitted into the production UI bundle.

## What this does not prove
