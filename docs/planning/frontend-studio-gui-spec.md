# Frontend Studio — GUI/UX specification

**Version:** v1.2 (2026-08-24; §12 mobile targets added). **Status:**
proposed spec — awaiting charter integration. This is a work-planning/design document, not an EDR; it creates
no Project Truth rows and modifies no contract. It specifies the GUI surface
for the Frontend Studio workstream chartered in
`docs/planning/product-studio-charter.md` (missions DDE-065..068) and is
written so DDE-067's implementer can build directly from it. Every file,
schema field, enum value, and endpoint cited below was verified against the
repo at commit `59978ac`.

The owner's three asks, verbatim intent: add features/elements/animations to
sites/apps **by pressing a button or dragging & dropping**, with **live edits
in the preview** — edit what you see, see it change immediately. Section 4
defines each as a precise interaction contract; Section 5 makes every one of
them a Gateway command.

## 1. Purpose & relationship to existing surfaces

Frontend Studio is **not a parallel app**. It is the evolution of the
existing DDE Code extension's webview surface
(`interfaces/dde-studio/**`) into the product-generation GUI the charter's
DDE-067 mission describes: accept a PRD, trigger compilation, browse grouped
donor results, and author/refine generated screens against the durable
prototype artifacts.

Hard architectural laws, inherited unchanged:

- **Gateway-client only, never Core tables.** All reads and writes flow
  through the live Gateway `/v1` surface via the typed client
  `interfaces/dde-studio/shared/gatewayClient.ts`
  (`GatewayApiClient`: sessions, `acceptCommand`, mission/mission-control
  reads) exactly as the extension does today. No view opens a database
  connection, reads a Core row, or bypasses the command plane. This is the
  charter's DDE-067 Scope IN ("Lives in `interfaces/dde-studio/**`,
  Gateway-client only") and REV_2_0 Ch.15's Gateway rule.
- **The durable artifact is the truth; the canvas is a projection.** Every
  visible pixel traces to `prototypes/screens/*.html` +
  `prototypes/flows.json` (validated by
  `schemas/design/prototype_flow.schema.json`, mechanically checked by
  `engine/verification/prototypes.py`). Editing changes artifacts through
  commands; it never patches the preview DOM as if the DOM were state
  (AGENTS.md forbidden list: no second source of truth).
- **Read-only streaming stays read-only where it is read-only today.**
  `src/webviews/previewGalleryProvider.ts` live-streams the workspace
  `prototypes/` directory into a sandboxed iframe (`srcdoc`,
  `GALLERY_IFRAME_SANDBOX = "allow-scripts"` without same-origin,
  `GALLERY_PREVIEW_CSP = default-src 'none'; …` — playbook §5.3 law,
  enforced host-side in `shared/ui/previewGallery.ts`). The Canvas reuses
  this exact sandbox for rendering; interactivity is added as *commands
  out* (webview message → Gateway), never as relaxed sandboxing.
- **Token SSOT governs everything the GUI offers.** Palette, spacing,
  radius, shadow, typography, durations, easings shown anywhere in the GUI
  come only from `schemas/design/tokens.json` via the generated module
  `shared/ui/tokens.ts` (regenerated by `scripts/generate_design_tokens`;
  hand-edits fail the drift check). The GUI never hardcodes a value the
  token sheet owns.

Relationship to the charter missions: DDE-065 supplies the compiled
generation prompt (with provenance) displayed in Intake; DDE-066 supplies
the grouped donor taxonomy rendered in Donors and mirrored in the Canvas
palette; DDE-068 supplies the quality verdicts rendered in Verify. This
spec is the DDE-067 consumption surface for all three, plus the authoring
grammar that closes the refine-in-place loop (playbook §5.0 P3).

## 2. Information architecture / navigation

Frontend Studio adds one activity-bar container group to the existing
`dde-studio` views container (`package.json` → `viewsContainers.activitybar`
→ `"dde-studio"`), reusing the established webview-view pattern
(`type: "webview"` entries with `media/icon-*.svg`). Cognitive load is held
at **six top-level views**:

| # | View (view id) | Purpose | Primary data source |
|---|---|---|---|
| 1 | **Home** (`dde.studio.frontend.home`) | Mission/PRD status board: which project, which approved PRD, compile state, active authoring mission | Gateway mission reads (`GET /missions/{id}`, `GET /mission-control/{id}`); list endpoints when they land (§9, D3) |
| 2 | **Intake** (`dde.studio.frontend.intake`) | PRD intake → compiled generation-prompt display with full provenance (input artifact ids + versions pinned by DDE-065) | Compiled-prompt artifact via Gateway |
| 3 | **Donors** (`dde.studio.frontend.donors`) | Manual pin-by-URL + DDE-066 grouped results by feature category, licence-class and taint badges, adoption state | DDE-046 ingest (`source_uri`) + grouped-results schema (DDE-066), Gateway reads/commands |
| 4 | **Canvas** (`dde.studio.frontend.canvas`) | Screens × states editor: three-pane workspace (§3), including the Motion workspace (§4.4) | Workspace `prototypes/` stream + manifest mutations via commands |
| 5 | **Verify** (`dde.studio.frontend.verify`) | Gate battery results: prototype-manifest findings, DD-lints, silhouette, density scorecard, VLM critique rounds, reduced-motion | VerificationRun/Evidence projections via Gateway (DDE-068 verdicts) |
| 6 | **Approvals** (`dde.studio.frontend.approvals`) | `donor_reuse` adoptions, budget requests, pixel sign-off queue | Existing approvals surface (`engine/governance/types.py` vocabulary) |

Deliberate IA decision: the owner-facing list in the charter discussion
names Motion as a seventh destination; this spec folds it **inside Canvas**
as a dedicated inspector workspace (deep-linkable via
`dde.studio.openMotionWorkspace` command) rather than a seventh rail icon.
Rationale: motion specs bind to a *selected element or transition*
(§4.4); a standalone view would force users to re-select context on every
use. Six icons, one muscle memory.

Existing control-plane views (Overview, Connection, Mission, Hermes/Claude
Code/DeepSeek, Verification, Approvals, Chat, Preview, Debug, Knowledge,
Evaluate, Integration, Context, Routing, Donors) remain untouched. The
existing read-only `dde.studio.preview` Prototype Gallery stays exactly as
it is; Canvas is its interactive sibling and links back to it for the
raw-gallery view. Renaming the control-plane extension remains out of
scope (charter DDE-067 Scope OUT).

Navigation rules:

- Views are reachable by keyboard from the activity bar (native VS Code
  behavior); each view registers a `when`-scoped title action for refresh.
- Cross-view deep links are ordinary commands (e.g. a Verify row links to
  the offending screen in Canvas via `dde.studio.openCanvasScreen`).
- No view nests more than two levels (rail → pane → panel); nothing hides
  behind accordions that a first-session user cannot discover.

## 3. Canvas workspace (three-pane)

The Canvas view composes three panes. Layout follows the declared
mission-control columnar shell pattern (playbook §4 guardrail 11 —
one-surface-one-pattern; the three-pane editor shell is declared here as
the Canvas pattern so it is auditable, not improvised).

### 3.1 Left pane — structure tree + component palette

Two stacked regions:

**(a) Screen/flow tree.** Renders the manifest model: every entry of
`screens[]` grouped by `surface`, each showing its `state` suffix
(the `file`/`surface`/`state` triple from
`schemas/design/prototype_flow.schema.json`), and every flow from
`flows[]` with its `steps` (`from --on--> to`). Selecting a tree node
loads it into the center canvas. Flow steps are selectable to expose their
`animation` (an `AnimationRef`) and `stateAnnotation` in the inspector.
Tree badges mirror mechanical validation: any finding kind emitted by
`engine/verification/prototypes.py` (`declared_screen_missing`,
`undeclared_screen_file`, `referenced_screen_missing`, `steps_empty`,
`flow_id_invalid`, …) shows as an error badge on the offending node, so
authoring and verification share one vocabulary.

**(b) Component palette, grouped by PRD-derived feature category.** The
groups mirror DDE-066's taxonomy exactly — the same
`feature_categories[]` the donor search used — so "add a checkout"
literally lists vetted donor components tagged `checkout`. Each palette
item carries:

- name and thumbnail;
- donor provenance where applicable: `source_class` (Ch.13.8 six-value
  scale), `licence_class`, taint tags, `provenance.url/ref` on hover —
  the fields of the grouped-results schema from the charter's pipeline
  sketch (`donor_id`, `source_class`, `licence_class`, `taint_tags[]`,
  `feature_categories[]`, `provenance{url,ref,retrieved_at}`,
  `adoption_state`);
- an adoption-state chip (`identified | screened | approved | rejected`)
  driving insert eligibility: only `approved` (`donor_reuse` recorded)
  donors insert cleanly; anything else presents the Adopt flow (§5) or a
  typed refusal, never a silent downgrade;
- an `unmatched` bucket at the bottom for results the grouping could not
  place (no silent drops — charter DDE-066 AC).

Base (non-donor) primitives (layout containers, text, buttons) come from
the product's own component inventory once the art-direction record lands
(playbook §10.1); until then the palette shows only what the compiled
prompt and donor results actually contain — an empty group says so (§6).

### 3.2 Center pane — live preview canvas

- **Sandboxed rendering, identical to the Gallery:** each screen renders
  in an iframe using the exact §5.3 constants (`GALLERY_IFRAME_SANDBOX`,
  `GALLERY_PREVIEW_CSP`) applied host-side before content reaches the
  frame. Self-containment is preserved: screens remain single-file HTML
  with inline styles referencing token variables only
  (`constraints.selfContained` / `constraints.tokenizedStyles` stay true
  through every edit; an edit that would violate them is refused with a
  typed error, not silently rewritten).
- **Device frames + breakpoint switcher:** 320 / 900 / 1280 px — the same
  widths the visual harness goldens assert
  (`interfaces/dde-studio/visual/screens.spec.ts`,
  `playwright.config.ts`; playbook §4 guardrail 18 density/viewport
  matrix). One click re-renders the selected screen at another width;
  the choice persists per editing session.
- **State selector:** wired to the manifest — picking among the declared
  `screens[].state` values for the current surface loads that state's
  screen file. States not yet authored are listed as absent (honest
  listing, not a placeholder frame).
- **Selection model:** elements carry stable `data-dde-el` anchors
  assigned at authoring/generation time. Click selects; the anchor id —
  never a runtime DOM path — is what commands address. Selection draws a
  chrome-level highlight overlay *outside* the sandboxed document (an
  inset outline aligned to the iframe's bounding boxes), so the preview
  document itself is never mutated by chrome.
- **Flow tracing:** a flow step can be "played": the canvas navigates
  `from` → executes the `on` trigger → arrives at `to`, honoring the
  step's `animation` tokens, so motion edits (§4.4) are judged on the
  real transition.

### 3.3 Right pane — contextual inspector

Binds to the current selection (element, flow step, or screen):

- **Properties:** the element's semantic props from its component record
  (label, variant, size class…), each rendered as a constrained control.
- **Token-bound value pickers:** color, spacing, radius, shadow, and type
  controls are dropdowns/swatches enumerating the semantic aliases from
  the token sheet (`--surface-base`, `--text-primary`, `--accent-primary`,
  `--status-ok`, `--focus-ring`, `spacing space0–space8`, radius
  `sm/md/lg/pill`, type scale `xs/sm/body/md/lg`). There is no free-form
  input (law in §4.5).
- **Variant switcher:** component variants as declared in the component's
  record; unknown variants cannot be typed in, only chosen.
- **Motion workspace (Motion tab):** §4.4.
- **Provenance footer:** for donor-derived selections, the taint chain
  (donor id → retrieval URL/ref/date → adopting approval id), satisfying
  Ch.13.8's "which donor evidence influenced this artifact" question at
  the element level.

## 4. Interaction grammar

This section is the precise contract for the owner's core asks. Two
invariants hold across all four gestures:

- **I1 — One code path per effect.** Button-click, drag-and-drop, and any
  future gesture produce the *same structured command* with the same
  payload schema. Gestures differ only in how the target position is
  chosen.
- **I2 — Structured mutations only.** Every edit is a manifest/artifact
  mutation expressed as a Gateway command (§5). Raw HTML injection into
  the preview, ad-hoc DOM patches, and client-side "temporary" states
  that pretend to be saved are all forbidden.

### 4.1 Add-by-button

1. User focuses a palette item (Tab/arrow keys — §7) and presses Enter or
   Space, or clicks it with the pointer.
2. If no screen is selected, the command is refused client-side with a
   typed hint naming the missing precondition ("Select a screen in the
   tree first"); nothing is inserted anywhere else "helpfully".
3. Default position rule: the component inserts at the sensible default
   slot for its category in the selected screen — root-level for layout
   containers, after the last sibling in the targeted region otherwise.
   The default slot is computed from the component record's declared
   parent affinity; when ambiguous, the canvas shows drop zones (§4.2)
   and asks, rather than guessing.
4. The insertion issues `frontend.canvas.insert_component` (payload:
   `screen_file`, `component_ref`, `anchor_parent`, `position_index`,
   `donor_id?`) — the identical command a drop produces.
5. Keyboard accessibility: every palette item is a real button element;
   the operation completes without pointer events; focus returns to the
   palette with an `aria-live` confirmation naming the inserted element.

### 4.2 Drag-and-drop

1. Pointer drag (or keyboard "lift and move" mode, §7) from a palette
   item enters the canvas; the canvas computes **layout-aware drop
   zones**: legal slots derived from the selected screen's structure and
   the dragged component's parent affinity. Illegal zones are not shown
   at all — the affordance teaches the layout grammar by only offering
   what the component model permits.
2. Drop targets are announced to assistive tech during keyboard move mode
   via `aria-live` region enumeration.
3. On drop, the zone resolves to `(anchor_parent, position_index)` and
   the SAME `frontend.canvas.insert_component` command fires with those
   coordinates. Drag adds zero new server-side concepts.
4. Drop cancel (Escape or drop outside any zone) issues nothing. A drag
   that ends without a legal target leaves no trace — no half-created
   elements, no orphaned ids.
5. Reordering existing elements is the same grammar: lift an element →
   zones appear → drop fires `frontend.canvas.move_component`
   (`element_id`, `new_anchor_parent`, `new_position_index`).

### 4.3 Live edit

The loop, end to end:

1. **Bind.** Click any element in the preview → the inspector binds to
   that element's `data-dde-el` anchor and populates from its component
   record. Binding is instant (chrome-local).
2. **Edit.** A property/token change in the inspector issues
   `frontend.canvas.update_element`
   (`screen_file`, `element_id`, `property`, `value` — `value` always a
   token alias or enum member, never a literal). Rapid consecutive edits
   to the same element+property coalesce within a short window into one
   command; each issued command still carries its own idempotency key.
3. **Round trip.** The command is accepted (HTTP 202 from
   `POST /v1/commands`), the engine-side handler mutates the durable
   artifact (screen HTML / manifest field / token override proposal),
   and the updated artifact reaches disk.
4. **Re-render.** The existing file-watch pipeline takes over — the same
   debounced watcher that drives the Prototype Gallery today
   (`previewGalleryProvider.ts`, `WATCH_DEBOUNCE_MS = 300`) pushes fresh
   `srcdoc` into the canvas iframe. What the user sees change *is the
   changed artifact*. Target: p95 under one second on a local Gateway;
   the budget is stated here so DDE-067 can be held to it.
5. **Failure.** If the command is refused (typed error, §5) the preview
   simply never changes, and the inspector flags the property with the
   verbatim error family/detail. There is no divergent "ghost" state
   where the UI shows an edit the artifact does not contain.

Two-tier feedback, honestly labeled: tier 1 is chrome-instant
(selection outline, inspector echo, `aria-live` acknowledgement); tier 2
is the artifact round trip above, which is when pixels change. The GUI
deliberately does NOT fake tier 2 with un-keyed client-side DOM
rewrites — a preview that lies about what is saved violates the honesty
law (§6) and the no-second-source-of-truth rule. Sub-round-trip pixel
echo is a named open item (§9, D8), not silent behavior.

**Undo stack.** Each editing session keeps a client-side undo stack of
its own issued commands. Undo applies the inverse mutation as a NEW
command (`*_undo` variants carrying `reverses_command_id`) with its own
idempotency key derived from the session's undo sequence number — undo
is never a replay-suppressed retry of the original. Redo mirrors it.
Approval-class effects (a `donor_reuse` adoption, a recorded pixel
sign-off) are NOT undoable from the canvas: crossing an approval boundary
requires a new explicit action on the Approvals surface. Undo of a
command whose target artifact changed since (lock_version/etag mismatch
surfaced by the typed error) is refused and surfaced, not force-applied.

**Write-back targets, exhaustively:** manifest fields
(`screens[]`, `assets[]`, `constraints`, `flows[].steps[].animation`),
screen HTML regenerated through the authoring pipeline from the element
model, and token override *proposals* (which ride the normal
tokens-edition flow — the GUI proposes; the token SSOT process decides;
the GUI never writes the generated module or the schema directly).

### 4.4 Animation adding (Motion workspace)

Entry: select an element or a flow step → Motion tab in the inspector.

1. **Presets from motion identity.** The preset list comes from the
   product's motion identity (playbook §10.6): named combinations over
   the token sheet's owned values — durations `fast/base/slow`
   (120/180/240 ms), easings `arrival/state/linear`
   (`cubic-bezier(0.16,1,0.3,1)`, `cubic-bezier(0.4,0,0.2,1)`,
   `linear`). Presets are tokens-owned configuration, not new literals.
2. **Parameters exposed = exactly what the schema supports.** For a flow
   step's `animation` (`AnimationRef` in
   `schemas/design/prototype_flow.schema.json`): `durationToken` (enum:
   `motion-duration-fast|base|slow`), `easingToken` (enum:
   `motion-easing-arrival|state|linear`), `reducedMotionVariant`
   (boolean), `boundedLoopMs` (integer, 0 < ms ≤ 2000). Trigger is the
   step's `on` selector (edited as a constrained picker over the
   screen's interactive anchors, not free text where avoidable).
   Parameters the schema does not yet carry — stagger, richer trigger
   grammars — are NOT exposed in v1; they appear only when the
   prototype-manifest schema extension lands (playbook §10.6; charter
   Definition-of-Polished gate 7 records these manifest fields as absent
   today). Exposing a control the schema cannot persist would manufacture
   a second truth.
3. **Instant preview.** Choosing a preset or parameter plays the
   transition on the canvas immediately: the flow-step player (§3.2)
   navigates `from` → `to` with the drafted `AnimationRef` applied as a
   preview-time overlay computed FROM the drafted values (equivalent CSS
   assembled from the same token variables), clearly badged
   "preview — not saved" until the command round trip replaces it with
   the re-rendered artifact. Reduced-motion degradation is demonstrated
   in the same play: the chrome's reduced-motion toggle (already present
   in the Gallery as `FORCE_REDUCED_MOTION_CSS`) forces the degraded
   variant so the author verifies end-states survive.
4. **Command.** Saving issues `frontend.motion.set_animation`
   (`flow_id`, `step_index`, `animation: AnimationRef`) — one more
   structured mutation; the write-back target is the manifest field
   itself.

### 4.5 Token-conformance by construction (hard law)

**There is no free-form color, font, spacing, radius, shadow, duration,
easing, or z-index input anywhere in the GUI.** Every such control is a
picker whose option list is enumerated from the token sheet via the
generated `tokens.ts` module: colors present semantic aliases (never raw
palette hexes — the schema itself documents that palette entries exist
only so aliases resolve); spacing offers `space0–space8`; radii
`sm/md/lg/pill`; type sizes `xs/sm/body/md/lg`; durations and easings
only the three-plus-three motion tokens; z-index only the ladder
(`content/sticky/skipLink/overlay/toast`).

Why this is stated as law rather than preference: DD201–DD206 (design
lints, `scripts/design_lints.py`, shrink-only baseline
`docs/design/lint-baseline.json`) ban exactly these literals — raw
hex/rgb outside the tokens module, off-scale spacing, font-family
literals, raw durations and cubic-bezier literals, gradient/backdrop
devices. A GUI that cannot emit a literal eliminates the violation
classes **at authoring time**, instead of catching them at CI time after
the mistake shipped. The lints then verify the pipeline rather than hunt
authors. The GUI additionally disables what it cannot guarantee: any
control whose value space the token sheet does not bound does not ship.

## 5. Command discipline

Every mutating gesture in every view is a Gateway command through
`GatewayApiClient.acceptCommand` — `commandId` (UUID), `idempotencyKey`
(UUID), `principalId`, `clientSessionId`, `targetType/targetId`,
`commandType`, `parameters` — hitting `POST /v1/commands` (202Accepted;
`engine/gateway/api.py`). This is the Ch.12.5 pattern as implemented by
`CommandLedger` in `engine/events/idempotency.py` and exercised by
`engine/planning/registry.py` (repeated key ⇒ stored result replayed;
previously-failed key ⇒ typed `VERSION_CONFLICT` refusal). Client-side
idempotency keys are minted per user gesture (one gesture = one key =
one effect, surviving retries and crashes).

Named command vocabulary (v1; `commandType` strings are proposals for
the DDE-067 contract addition, registered like any Gateway command
type):

| Gesture / action | commandType | Target |
|---|---|---|
| Insert (button or drop) | `frontend.canvas.insert_component` | screen file |
| Move/reorder | `frontend.canvas.move_component` | element |
| Property/token edit | `frontend.canvas.update_element` | element |
| Remove element | `frontend.canvas.remove_element` | element |
| Set/clear transition animation | `frontend.motion.set_animation` | flow step |
| Add/edit flow step | `frontend.flow.upsert_step` | flow |
| Trigger compile | `frontend.intake.compile_prompt` | PRD/mission |
| Run donor discovery | `frontend.donors.run_discovery` | mission |
| Pin donor by URL (paste address) | `frontend.donors.submit_uri` | mission / project |
| Request donor adoption | `frontend.donors.request_adoption` | donor result |
| Request pixel sign-off | `frontend.prototype.request_pixel_signoff` | prototypes set |

**Manual pin-by-URL (owner requirement, 2026-08-24):** the Donors view
exposes an address field ("Add donor URL") that submits
`frontend.donors.submit_uri` with the typed `source_uri`. Chat / MCP
clients that accept a pasted address MUST issue the **same** command —
they are clients of the Gateway, not a second ingest path and not model
authority over classification. Backend materialization is DDE-046
ingest → `DonorArtifact` (`adoption_state: identified`, default
`source_class: UNKNOWN` until DDE-047 classifies). Network fetch of the
URI is subject to the same egress admission as discovery (EDR-0015);
offline/fixture ingest may accept a local/fixture URI without egress.
Pinning never auto-adopts: use still requires `donor_reuse`.

Rules that bind every row of that table:

1. **Approval-class actions render as explicit confirmations/chips,
   never silent.** Requesting adoption of a donor (`donor_reuse`),
   anything budget-affecting (compile/discovery runs consume Ch.16.4
   budget), and publish/sign-off show a confirmation naming the
   approval type, its scope hash meaning, and who must decide. After the
   decision, a persistent chip on the affected object shows the approval
   status (`REQUESTED/UNDER_REVIEW/APPROVED/...` — the vocabulary of
   `engine/governance/types.py`). The GUI never treats a chat message,
   checkbox, or dismissal as an approval; approvals are approval-row
   writes on the ordinary Ch.13.1 propose/decide surface, matching the
   playbook §5.4 standard ("the approval is governance, not a
   thumbs-up emoji").
2. **Failed commands surface typed errors verbatim.** `GatewayApiError`
   (`errorFamily`, `detail`, `httpStatus`, `retryable` — the client's
   Ch.15 error-contract subset) is displayed as-is: family, detail, and
   the retryable flag driving whether a Retry affordance exists at all.
   No swallowed failures, no generic "something went wrong", no
   auto-retry of side-effecting operations outside the idempotency key
   (AGENTS.md forbidden list). Non-retryable refusals disable the
   originating control until its precondition changes.
3. **Optimistic state is bounded.** Only chrome-level feedback
   (selection, inspector echo, progress) is optimistic; durable-looking
   pixels wait for the artifact (§4.3). A crashed or closed session
   leaves at most a pending command with its idempotency key — recovery
   is a reconciliation read (session resume), never a blind re-fire.
4. **Every new capability this GUI exercises declares its
   `side_effect_class`** (Ch.9.3) on the engine side; the GUI displays
   that classification on confirmation dialogs for side-effecting
   commands, so the human sees what class of thing they are about to
   cause.

## 6. Honesty rules for the GUI itself

`shared/clientHonesty.test.ts` extends to cover every new view. The
existing mechanics generalize directly: the `FORBIDDEN_HELPER` regex
list, the no-stub/no-fake assertions
(`PendingGatewayClient` returns truly empty lists; HTML must not match
`mission_stub|run_stub|event_stub`), and the disabled-until-real
pattern (the approvals batch button ships disabled with a factual
`title="approvals read surface pending"` until a read surface exists —
the same posture applies to every new affordance below).

Per-view honesty requirements:

- **Empty states say what is missing and why, with the next real
  action.** Composed per playbook guardrail 10 (icon + one-line factual
  title, zero instructional essays): Donors with no results —
  "No donor results yet — run discovery" (+ the Run control, enabled
  only when discovery is actually admitted, i.e. EDR-0015 accepted);
  Intake before compilation — "No compiled prompt yet — approve a PRD
  and run compilation"; Canvas with no screens — "No screens yet —
  generate from Intake or open a workspace with prototypes/"; Verify
  before a run — "No verification run yet".
- **No placeholder/fabricated screens, scores, rows, or badges.** Ever.
  No mock quality verdicts before DDE-068 lands, no sample donor rows,
  no lorem screens in any shipped view. Where a capability is pending
  (EDR-0015 egress, EDR-0016 critic, D3 list endpoints), the control is
  disabled with a factual reason string — the pattern the suite already
  enforces — and the reason names the admitting decision, not an essay.
- **VLM critique scores display raw, with round number, never smoothed,
  averaged, or color-washed into false comfort.** Round 2 of 3, per-
  dimension rubric values, residuals listed. Rank-9 discipline made
  visible: critiques inform; the UI labels them as model-assisted
  evidence that never auto-applies (charter guardrail 7).
- **Gate statuses in Verify mirror the charter's Definition-of-Polished
  battery exactly** — including showing gates that are not yet
  enforceable as explicitly deferred (named landing mission), never as
  green. A gate without a wired call site renders as "deferred",
  mirroring the chapter-gate rule in the UI itself.
- **Prototype-manifest findings render with their mechanical kind and
  path** (`declared_screen_missing` at `screens/foo.html` …), the same
  strings `engine/verification/prototypes.py` emits — no paraphrase
  layer that could drift from the verifier.
- **Copy law:** verb-first buttons, sentence case, no marketing
  superlatives, no emoji — the binding rule file's nevers apply to the
  studio chrome with full force; the studio is itself a DDE surface.

## 7. Accessibility & keyboard support of the tool itself

- **Full keyboard paths for every gesture in §4.** Palette: Tab into the
  palette, arrows between items, Enter/Space = add-by-button. Move:
  a keyboard lift/move mode (Enter lifts, arrows walk announced drop
  zones, Enter drops, Escape cancels) so drag-and-drop has a complete
  non-pointer equivalent issuing identical commands. Inspector: every
  control is a native form element, reachable in DOM order; the Motion
  tab's preset list is a listbox with type-ahead. Nothing in the
  authoring grammar requires precision pointing.
- **Focus and announcements.** `:focus-visible` rings and skip-link
  conventions carried from `shared/ui/base.ts` (guardrail 9 — do not
  regress); `aria-live="polite"` regions announce command outcomes
  ("Inserted Button in checkout.ready"), errors announce with their
  family. Dialog-grade confirmations trap focus and close on Escape.
- **Reduced-motion respected in the studio chrome itself.** All chrome
  animation rides the motion tokens and honors `prefers-reduced-motion:
  reduce` (end-states preserved, spatial movement removed) — the same
  law the GUI enforces on generated products (playbook §5.2). The
  Gallery's forced-reduced toggle gains a Canvas equivalent so authors
  can verify degradation without changing their OS setting.
- **Contrast and theme triad under the same token law.** The studio UI
  consumes the same generated tokens (`tokenCssRoot()`); text/UI pairs
  meet WCAG AA (≥4.5:1 text, ≥3:1 large/UI) at design time in the token
  sheet (guardrail 12); usable under `vscode-light`, `vscode-dark`, and
  `vscode-high-contrast`; every `var(--vscode-*)` read keeps its literal
  fallback. Target-size follows the existing 28px-button standard
  (guardrail 9), above the SC 2.5.8 minimum.
- **Verification.** The axe scan tags (`wcag2a, wcag2aa, wcag22aa`,
  zero critical/serious) already running in the visual harness job
  extend to Canvas fixtures; the manual keyboard walk (Tab order, traps,
  Escape) stays a review checklist item per guardrail 9.

## 8. Non-goals (v1)

- **No freehand code editor replacing the artifact model.** The host IDE
  remains available for raw HTML/JSON editing by humans and workers;
  the GUI neither wraps nor hides it. But the GUI's own editing surface
  speaks components/manifests/commands, not source text.
- **No direct DOM manipulation of the preview.** No contentEditable
  canvas, no drag-resize of arbitrary boxes that would mutate pixels
  without an artifact. Selection, zones, and highlights live in chrome;
  documents change only via artifact regeneration.
- **No bypassing approvals.** No "quick adopt" path around
  `donor_reuse`, no sign-off shortcut, no standing-approval widening to
  make a flow smoother (AGENTS.md forbidden list).
- **No network calls outside admitted EDRs.** Donor search waits for
  EDR-0015; VLM critique display waits for EDR-0016; the GUI itself
  makes zero outbound connections beyond the configured Gateway
  (`dde.studio.coreUrl` / optional cloud target).
- **No second source of truth.** No client-side database, no cached
  manifest that can diverge, no localStorage state that survives as
  pseudo-artifact. Session state is a projection + undo stack, both
  rebuildable from the Gateway.
- **No collaborative cursors / multi-user live co-editing in v1** (§9,
  D5). Sessions are per-principal; concurrent edits resolve through
  command ordering and lock versions, with conflicts surfaced as typed
  errors, not merged silently.
- **No renaming the control-plane extension** and no fork of the
  GatewayClient — one client, one `/v1` surface (charter Scope OUT).

## 11. Professional-platform parity roadmap (2026-08-24)

Owner question: how else can Frontend Studio be improved to create a
development environment matching other professional platforms? Method:
benchmark the spec against named capabilities of the platforms
professionals actually use, classify each gap into exactly one bucket,
and respect this spec's laws (token-conformance-by-construction §4.5,
honesty §6, keyed commands §5, approval boundaries §4.3/§5) everywhere a
platform feature would collide with them. Precedents were verified
against current product documentation and 2026 comparisons; where a
precedent's mechanism is described, it is named so the claim can be
re-checked.

Buckets: **A** already in spec · **B** cheap v1 addition (fits existing
contracts, no new EDR — rides a named command/schema surface) · **C**
v2 feature (needs schema extension or new mission scope) · **D** needs
EDR/new mission (network, model calls, budget, or governance
implications).

### 11.2 Top items, in prose

**P4 — Multi-select batch edit (B).** Figma's multi-edit exists because
repeating one change N times is the tax professional tools eliminate.
Our command plane already treats a gesture as one keyed unit, so a batch
is simply a command whose payload carries many targets — no new
governance surface, no schema change (element ids are already stable
anchors). This is the largest authoring-speed gain available inside v1's
contracts.

**P2 + P3 — pending edits with before/after, then per-edit visual diff
(B).** Together these reproduce v0 Design Mode's core loop — tweak
pending, compare, apply as a diffable version — while staying honest:
the draft lives in inspector state, "before" always means the artifact
on disk, and applying is the ordinary keyed command. The diff half rides
the existing Phase-B screenshot capability; nothing about it fabricates
state. Note this also *resolves* much of open item D8: instead of
optimistic pixel echo (which risks lying about persistence), the author
gets deliberate preview control — a stronger affordance than latency
sugar.

**P5 + P6 + P14 — the inspection triad (B).** Computed styles, layout-
shift attribution, and axe overlays convert the canvas from a viewer
into a debugger. All three are read-only projections: measurement
channels through the existing sandboxed iframe boundary (messages out),
results rendered in chrome. They reuse the exact harness (Playwright +
axe tags) DDE-068 already runs in CI — moving verdicts from post-hoc CI
red into the authoring moment.

**P15 — flow-graph visualizer (B).** The manifest is already a graph;
`flows[]` steps are edges with trigger labels. Professionals reason
about navigation structurally; a two-column tree (§3.1a) hides cycles
and orphaned screens that a node-link view exposes instantly.

**P1 — command palette (B).** The cheapest item with the highest daily
habit value. Every action named anywhere in this spec becomes a
registered VS Code command; `Ctrl+Shift+P` then covers add/move/
motion/sign-off without touching the mouse. It also future-proofs
discoverability as views grow.

**P9/P10 — the AI-builder gaps (D).** What Lovable/v0 give users that
we deliberately do not yet have is prompt-to-edit on selection and
parallel candidate generation. Both involve model calls at authoring
time and both produce rank-9 material: proposed structured commands and
alternative artifacts that must inform, never auto-apply. The right
instruments are EDR-0016 scope extension (or successor) plus explicit
budget lines — the mechanisms exist (approvals, Ch.16.4), so these are
admission questions, not architecture questions.

**P17–P19 — the responsive/theming tier (C).** Breakpoint overrides,
per-component constraints, and token modes are how Webflow/Framer users
get products that survive contact with real devices and dark-mode
requirements. All three are schema extensions (manifest property
dimension, component record fields, token mode axis) — correctly v2,
correctly additive-first, none urgent before first real compile.

### 11.3 Platform capabilities judged NOT worth adopting

- **Freehand CSS/source editing inside the studio (rejected).** Webflow
  embeds and builder code panes optimize for flexibility; our §4.5 law
  optimizes for making DD201–206 violations unrepresentable. A raw CSS
  input would reintroduce exactly the literal classes the lints ban and
  force the pipeline back to catch-after-the-mistake. The host IDE
  remains the escape hatch (§8), where edits face the same CI gates.
  Professionals solve the underlying need (escape the picker grid)
  within constraint systems — v0 surfaces "Tailwind-compatible values",
  i.e. constrained vocabularies, not arbitrary CSS; our equivalent is
  richer token-bound pickers (P11), not free input.
- **Multi-user live cursors (already deferred, §8/D5)** — high
  infrastructure cost, low solo-author value today; revisit when
  team-based authoring missions exist.
- **Auto-applying AI suggestions (not adopted as such).** Lovable-class
  tools write changes straight into source on your behalf. Under DDE's
  rank discipline, model output is evidence that informs; adoption of
  the resulting structured commands remains a human gesture (or an
  autonomy-bounded worker action governed by existing rules). P9/P10
  adopt the *experience* within that boundary.

### 11.4 Law-conflict flags

- **Optimistic DOM echo (v0 applies tweaks live in-preview):** violates
  §4.3's honesty tiering if pixels move before the artifact does. Our
  resolution is P2's pending-edit layer — preview by explicit user act,
  badged as unsaved — rather than automatic echo (refines D8).
- **One-click "Apply" that bypasses review:** v0 serializes Apply into
  a chat version; our analogue must remain the keyed command with its
  typed-error path (§5) — batch (P4) included: one gesture, one key,
  one effect, all-or-nothing refusal semantics.
- **Comment threads as approval substitutes (Figma-style):** pins (P8)
  are annotations; they can *feed* the sign-off queue but never
  constitute sign-off (playbook §5.4: governance, not a thumbs-up
  emoji).
- **Variant generation discarding losers silently:** even discarded
  candidates are derived evidence; retention follows whatever
  EDR-0016-class policy decides, and the GUI shows what happened to
  them (honesty law applied to process, mirroring §6's gate-status
  rule).

## 12. Mobile targets — Expo/React Native, Capacitor, Flutter (assessed), Jetpack Compose (2026-08-24)

**Status:** web remains DDE-067's v1 scope unchanged — nothing in §§1–11
is resized by this section. Mobile enters as a provisionally-numbered
**DDE-069 "Mobile Profiles" mission** whose charter defines (a) the
token-generator extension below, (b) per-target renderer adapters behind
the capability contract, and (c) per-target acceptance criteria. Per
house rules, DDE-069 files an **EDR for multi-platform artifact
generation** before implementation starts (the EDR-0008/0015/0016
accept-first pattern: charter written now, implementation gated on
acceptance). This section specifies intent and seams, not admitted
dependencies.

### 12.1 Multi-target token SSOT

One sheet, many themes: `schemas/design/tokens.json` stays the single
source of truth, and `scripts/generate_design_tokens.py` grows from one
emitter to several. The generator's structure makes this a clean seam:
`render()` already returns a `dict[Path, str]` of outputs and `--check`
diffs every registered file, so each new target registers one more
generated artifact under the same drift gate:

- **Web (exists today):** `interfaces/dde-studio/shared/ui/tokens.ts` —
  typed constants + `tokenCssRoot()` CSS string.
- **React Native:** a generated StyleSheet theme module — token leaves
  become style constants (`spacing` numbers in dp, palette hexes,
  duration ms); easings translate to RN's `Easing` equivalents where
  they map, and unmappable values surface as generator refusals rather
  than silent approximations.
- **Jetpack Compose:** a generated Material 3 theme package
  (`Color.kt` / `Type.kt` / `Theme.kt`) — palette entries map to M3
  color-scheme slots via an explicit alias table in the generator;
  spacing/type/motion become typed Kotlin constants. The mapping table
  is reviewed code, not convention.
- **Flutter (optional):** a `ThemeData` builder module.

Conformance-by-construction survives everywhere: the GUI's pickers are
per-target and enumerate ONLY values from that target's generated theme
module — there is no free-form color/font/spacing input on any platform
(§4.5 is target-independent law). DD-lint law extends per-target with
one honest gap statement: **per-non-web-target lint implementations do
not exist today and land with DDE-069**; until then, non-web artifacts
are governed by the generated-theme-only rule plus review, never by a
claimed-but-unwired lint.

### 12.2 Manifest target profile

Screens × states × flows stay THE durable artifact model — no second
truth per platform (AGENTS.md forbidden list). A `target` profile
dimension routes renderers: the same manifest entry renders as web HTML,
an RN screen, or a Compose screen according to its profile, behind the
capability contract — each renderer adapter declares its Ch.9.3
side-effect class like any capability. The keyed-command grammar of §5
is unchanged across targets: `frontend.canvas.insert_component`,
`update_element`, `move_component`, `frontend.motion.set_animation`
address elements through stable anchors exactly as on web; only the
artifact the engine-side handler regenerates differs (HTML vs
Kotlin/TSX). Undo, idempotency keys, typed-error surfacing, and approval
boundaries all inherit unchanged.

### 12.3 Per-target live-edit channels (the owner's core ask, per platform)

Real-time add/components while watching the app, per target:

- **Web:** existing srcdoc/watcher pipeline (§4.3); the p95 <1 s budget
  stands.
- **Expo/React Native:** the canvas embeds Expo's dev client; edits
  push over Expo's HMR channel so components appear on device/simulator
  in real time. The command round trip is identical to web (keyed
  command → artifact regenerated → dev-client reload), with Expo's
  channel replacing the srcdoc watcher as the re-render leg.
- **Jetpack Compose:** same command grammar writes the Kotlin artifact
  (generated theme + composables) → incremental Gradle install to the
  running emulator over an adb push loop (seconds-class refresh).
  Additionally, composables are authored `@Preview`-compatible so the
  canvas can render instant static previews WITHOUT an emulator — the
  fast feedback tier sits inside DDE's own canvas; emulator refresh is
  the fidelity tier.
- **Capacitor:** wrapped-site path inherits the ENTIRE web pipeline
  unchanged — the web artifact is the app content, making Capacitor the
  cheapest route from prototype to "app" distribution. No separate live
  channel exists because none is needed.
- **Flutter:** assessed, deferred. Dart/token story diverges from the
  TS-anchored token law today (separate toolchain, separate package
  ecosystem); revisit only if product demand materializes. Nothing in
  the schema or generator precludes it later — it would be one more
  emitter in the dict above.

### 12.4 Governance

- **No new egress class:** local dev loops need no network beyond
  ordinary dependency resolution (npm/Maven caches) — the same posture
  as CI today. Emulator/simulator traffic is local. Anything beyond
  that (remote device farms, cloud builds) is out of scope here and
  would be an EDR-0015-class admission question.
- **No new approval types:** donor adoption still rides `donor_reuse`
  regardless of target platform — Ch.13.8 classification and taint
  apply per-platform too (an approved web donor is not automatically an
  approved RN/Compose donor; provenance records which target a result
  was vetted for).
- **Quality gates extend per-target, named not invented:** Playwright
  web gates exist via EDR-0008 Phase B; Detox/Maestro-class native
  visual+interaction gates are named as DDE-068's future mobile
  extension — their admission, budgets, and rubric applicability belong
  to that mission, and until wired they render as "deferred" in Verify
  (§6 law).
