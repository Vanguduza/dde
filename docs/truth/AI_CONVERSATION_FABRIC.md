# DDE AI Conversation Fabric — Canonical Product & Runtime Architecture

**Status:** USER-LOCKED DDE-069 EXTENSION (2026-09-05)
**Authority:** AD-042 + Rev 3 Blueprint/Dev Plan.
**Depends on:** `CURSOR_CLASS_AI_CHAT.md`, Gateway/Core authority, TaskGraph, Workspace, CapabilityLease, Approval, Verification/Evidence.

## 1. Purpose

DDE Chat is the conversational operating surface over DDE, not a provider-owned chatbot. Claude Code, Codex, Hermes, OpenAI-compatible models and future harnesses are replaceable reasoning/execution providers behind DDE-owned state.

DDE owns history, project identity, memory authority, plans, permissions, tool admission, workspaces, evidence, verification, recovery and promotion. A provider may reason or execute only inside the authority DDE grants.

## 2. Non-negotiable laws

1. Provider state is never Project Truth.
2. Installed/documented capability is not certified capability.
3. Ask is read-only; Plan may propose durable work; Execute still uses Gateway/Worker/Capability authority.
4. Provider resume/session identifiers are opaque lineage only; no credentials are persisted in conversation records.
5. Provider fallback is visible and attributable.
6. Tool calls and subagents are visible activities, never hidden in assistant prose.
7. Memory is scoped, provenance-labelled and approval-governed; inferred memory never silently becomes authoritative.
8. Compaction always produces an inspectable durable context snapshot before context is discarded.
9. Skills/plugins/MCP servers are supply-chain inputs and require admission/certification before executable use.
10. Child agents receive bounded context, tools, workspace and budget; delegation cannot widen parent authority.
11. Research sources, claims, hypotheses and confidence remain distinguishable.
12. Schedules/hooks compile to the same governed command path as interactive actions.
13. Model/harness/tool/skill identity is part of run lineage and evaluation.
14. No provider-specific feature may require rewriting canonical conversation history.

## 3. Fabric domains

The fabric comprises:

- ConversationPolicy — reasoning effort, permission profile, toolsets, fallback chain and budgets.
- WorkerSession — long-lived harness/session lineage as already required by Blueprint §9.
- ProviderInvocation — one model/harness invocation with exact requested/serving identity, usage and fallback lineage.
- AgentInteropEndpoint — discovered/certified NATIVE_CLI/NATIVE_SDK/ACP/MCP/HTTP endpoint capability.
- ProviderCapacitySnapshot — health/quota/rate-limit/cost observations used by routing, never guessed by UI.
- MemoryItem — scoped candidate/approved memory with trust/provenance.
- ContextSnapshot — explicit retained/omitted context and compaction lineage.
- Skill — versioned candidate/evaluated/certified skill with provenance and required capabilities.
- AgentTeam — bounded manager/member topology linked to tasks/workspaces/sessions.
- ResearchArtifact — cited source ledger, findings, competing hypotheses and unresolved questions.
- Automation — one-time/interval/cron/condition future work request.
- ConversationHook — Before/After lifecycle hook that proposes governed actions.
- Claim — per-turn epistemic annotation: repository fact, external source, inference, proposal or unknown.

## 4. Conversation policy

Each conversation selects or owns a durable policy containing:

- reasoning effort: FAST/NORMAL/DEEP/MAXIMUM;
- permission profile: READ_ONLY/WORKSPACE_EDIT/AUTONOMOUS_LOCAL/APPROVAL_GATED;
- admitted toolset IDs and explicitly denied capabilities;
- provider/model fallback chain;
- maximum turns, context tokens and cost budget;
- quality/latency priorities;
- whether independent review/council is required.

Provider adapters translate this policy into provider-native flags only after DDE legality checks. `--yolo`, dangerous permission bypasses and equivalent flags are never generated by normal profiles.

## 5. Provider/session federation

A DDE conversation may bind multiple provider sessions. DDE can resume, detach, fork or replace a provider session without branching canonical conversation history.

Every provider session records:

- harness/provider/install/version;
- opaque provider session reference;
- workspace/project binding;
- discovered and certified capabilities separately;
- requested model and serving-model evidence when available;
- current state and last activity;
- context/tool/config hashes.

The active provider for a turn is selected by policy/routing, not by provider memory.

## 6. Interoperability

DDE uses one AgentInteropLayer:

```text
DDE Conversation / TaskGraph
        ↓
AgentInteropLayer
 ├─ Claude native/CLI
 ├─ Codex native/app-server/CLI
 ├─ ACP → Hermes/future agents
 ├─ MCP tool/resource servers
 └─ HTTP/OpenAI-compatible providers
```

Capability discovery is version-specific. Discovery may use harmless `--version`/`--help`/protocol initialize probes. Certification requires contract tests and never follows automatically from discovery.

## 7. Invocation and routing lineage

Every generative turn creates a ProviderInvocation before execution. It records requested profile/model, chosen endpoint, reasoning level, context hash, prompt hash, policy hash and approval lineage. Completion records serving model if attested, input/output/cache/reasoning tokens, latency, cost, provider status, result refs and fallback parent.

Fallback is a sequence of independently recorded invocations; the UI must show the provider that actually answered.

## 8. Memory and context

Memory scopes:

```text
USER → ORGANIZATION → PROJECT → REPOSITORY → MISSION → CONVERSATION → EPHEMERAL
```

Trust classes:

- AUTHORITY — copied from durable DDE truth/evidence;
- DERIVED — computed from authoritative inputs with provenance;
- ADVISORY — provider/user suggestion;
- UNKNOWN.

Provider-proposed memories enter CANDIDATE state. APPROVED is an explicit DDE action. Rejected/superseded memories remain auditable.

### 8.1 Durable shared-memory storage

PostgreSQL is the authority/index layer for memory identity, scope, trust, promotion, freshness, hashes and provenance. Non-ephemeral full memory bodies are content-addressed in DDE durable object storage under `memory/<tenant>/<project>/<sha256>`. Context/compaction archives use the same scoped object law under the `context` namespace; Chat attachments use `chat`. Cloudflare R2 is the production S3-compatible backend when complete scoped credentials are configured. Local content-addressed storage is the development fallback. Explicit `DDE_OBJECT_BACKEND=r2` fails closed when R2 configuration is incomplete. Provider credentials and R2 secrets are never written into memory or conversation records.

Hermes is not allowed to become a second memory authority. DDE-launched Hermes ACP is admitted only when the installed runtime passes ACP health under `--ignore-rules`; DDE then starts Hermes with that isolation flag so its automatic `MEMORY.md`/`USER.md`, project-rule and preloaded-skill injection cannot duplicate or contradict the DDE context package. Hermes may contribute observations/proposals through governed Fabric surfaces, but approved DDE memory is what becomes shared recall for Hermes, Claude, Codex, GPT-class and future providers.

### 8.2 Context and token allocation

Universal DDE Chat uses a conversation context manager rather than replaying an unbounded transcript. The conversation policy's `context_token_budget` is authoritative. Protected current prompt/live DDE authority is budgeted first; explicit/pinned refs, approved semantic memory and conversation history receive bounded allocations next. Memory recall is ranked by lexical relevance, trust class, scope, provenance and freshness, and large object-backed memories are hydrated/excerpted only after ranking. CANDIDATE/REJECTED/SUPERSEDED memories never enter provider context.

Warm resumable provider sessions receive a deliberately smaller history replay budget than cold sessions because the provider already holds session state. Older turns are compacted deterministically when needed. DDE persists PRE_COMPACTION/POST_COMPACTION ContextSnapshots containing retained refs, omitted refs/reasons, exact token estimates, summary, predecessor and content hash, with the complete manifest archived in durable object storage. The Chat Context panel exposes token utilization, memory/history allocation, archive backend and omissions so compaction is never silent.

## 9. Skills and learning

A DDE Skill is a versioned supply-chain artifact with source, license/provenance, manifest hash, instructions, required capabilities, tests/evaluation refs and lifecycle:

```text
CANDIDATE → EVALUATING → CERTIFIED → RETIRED
             └────────→ REJECTED
```

Hermes or any provider may propose a candidate skill from successful trajectories; only DDE evaluation/promotion can certify it. A skill cannot self-authorize tools or network access.

## 10. Agent teams

Agent teams are first-class DDE objects. Strategies include SPECIALIST_FANOUT, PARALLEL_IMPLEMENTATIONS, COUNCIL, REVIEW_PANEL and RESEARCH_SWARM. Members bind role, task, model/profile, provider session, workspace, toolset, budget and state.

Delegation limits include max depth, max children and aggregate budget. Child sessions cannot access parent-only secrets, approvals or write scopes. Results return as refs/evidence and are independently reviewable.

## 11. Research and councils

Research mode creates a ResearchArtifact rather than a prose-only answer. It stores:

- question/scope;
- source ledger with URL/file/ref, date, authority and retrieval metadata;
- findings;
- competing hypotheses;
- claim/evidence mapping;
- unresolved questions;
- confidence and freshness;
- conversion refs to requirements/EDRs/plans/tasks.

Compare/Council mode may run multiple admitted providers independently, then create a synthesis invocation whose inputs explicitly contain the competing results. The judge is not allowed to erase dissenting evidence.

## 12. Multimodal and voice

The existing attachment system is the universal multimodal ingress. Images, PDFs, logs, audio/video excerpts and code files remain typed attachments. Provider adapters advertise supported modalities. Unsupported extraction is explicit.

Voice is a transport over the same conversation: audio attachment → admitted transcription capability → ordinary user turn. No separate hidden voice history exists.

## 13. Hooks

Supported lifecycle events include:

- BEFORE_TURN / AFTER_TURN;
- BEFORE_CONTEXT / AFTER_CONTEXT;
- BEFORE_PROVIDER / AFTER_PROVIDER;
- BEFORE_TOOL / AFTER_TOOL;
- BEFORE_MUTATION / AFTER_MUTATION;
- BEFORE_VERIFICATION / AFTER_VERIFICATION;
- BEFORE_PROMOTION;
- BEFORE_COMPACTION / AFTER_COMPACTION;
- SESSION_START / SESSION_END;
- SUBAGENT_START / SUBAGENT_END.

Hooks may record telemetry, create checkpoints/memory candidates or propose a governed command. They do not directly bypass Gateway/Approval/Capability authority.

## 14. Scheduled and conditional work

Automations are durable rules owned by DDE. Schedule kinds are ONCE, INTERVAL, CRON and CONDITION. An evaluator identifies due rules and emits an ordinary governed action with an idempotency identity. Completion computes the next occurrence. Emergency pause disables dispatch without deleting rules.

## 15. MCP/ACP surfaces

DDE consumes MCP through admitted AgentInteropEndpoints. MCP tool discovery does not imply tool authorization. Every tool maps to a DDE capability/policy decision.

DDE also exposes a narrow MCP-compatible tool surface over existing reads/commands so external harnesses can inspect project/mission/chat/plan/verification/audit state and request governed commands. MCP never exposes direct table access.

ACP is the baseline agent-session transport for Hermes/future agents; native transports remain preferred where they expose richer certified capabilities.

## 16. Provider capacity and health

Capacity states follow Rev 3:
AVAILABLE, DEGRADED, QUOTA_PRESSURE, RATE_LIMITED, EXHAUSTED, COOLDOWN_UNTIL_RESET, REPROMOTION_ELIGIBLE, AUTH_REQUIRED, UNHEALTHY.

Snapshots record source/confidence/reset time, concurrency, latency, failures, token/cost metadata. Routing may consume them; a provider may not write its own routing policy.

## 17. Epistemic claims

Provider and deterministic answers may attach Claim rows. Classes:
REPOSITORY_FACT, EXTERNAL_SOURCE, INFERENCE, PROPOSAL, UNKNOWN.

Claims carry source refs, confidence and verification state. UI badges make proposal/inference visually distinct from repository evidence.

## 18. UI

Cursor-class Chat adds a Fabric drawer with:

- active provider/session + discovered/certified capability badges;
- reasoning, permission and toolset policy controls;
- fallback chain and provider health;
- context/memory inspector with approve/reject memory inbox;
- skills browser and candidate/certification state;
- agent-team tree with stop/steer controls;
- research source ledger/council comparison;
- automation/hook list;
- per-turn usage/cache/latency/cost and claim badges.

No panel may show a provider as active/certified without persisted evidence.

## 19. Integration with existing DDE missions

This DDE-069 extension lands the shared conversation-facing contracts, persistence, interop seams and UI now. It intentionally accelerates shared primitives planned in DDE-073 (Claude sessions/hooks), DDE-075 (ACP/Hermes experience intelligence) and DDE-076 (provider capacity/fleet truth). Those downstream missions retain their original acceptance gates for managed provider runtimes, full Hermes experience ingestion and fleet-wide certification. Early shared implementation does not auto-mark them complete.

## 20. Acceptance

The fabric is conformant only when tests prove:

1. provider discovery is factual and separate from certification;
2. session resume/fork lineage is durable;
3. Ask/Plan/Execute authority remains intact across provider calls;
4. fallback invocations are separately attributable;
5. memory candidates cannot self-promote;
6. compaction snapshots preserve retained/omitted provenance;
7. skill candidates cannot self-certify;
8. subagents cannot widen capability/workspace/budget scope;
9. research keeps source/claim provenance;
10. hooks/schedules re-enter Gateway rather than bypassing it;
11. MCP/ACP endpoints expose negotiated capabilities only;
12. provider capacity never fabricates availability;
13. unsupported external credentials/runtimes are typed unavailable;
14. existing Frontend mutation/verification/promotion gates still hold.
